n8n borra su propio histórico de ejecuciones (por defecto lo conserva unos días). Este servicio mantiene una copia acumulativa e independiente de todas tus ejecuciones, con búsqueda a texto completo, sin tocar nunca la base de datos de n8n. Esta guía explica cómo instalarlo al lado de un n8n que ya corre en Docker, las opciones que tienes y cómo elegir entre ellas.

1 · Cómo accede a la base de datos

Es la pregunta más importante y tiene una respuesta tranquilizadora: SQLite no es un servidor. No hay puerto, ni protocolo de red, ni usuario ni contraseña — como sí los hay en MySQL o Postgres. SQLite es un fichero (database.sqlite) que n8n escribe en su volumen de Docker.

Docker permite montar el mismo volumen en dos contenedores a la vez. El viewer monta el volumen de n8n en modo solo-lectura (:ro) y abre el fichero con el modo read-only del propio SQLite. n8n no participa en nada: no hay token, ni webhook, ni llamada a su API, ni siquiera sabe que el viewer existe.

TU SERVIDOR (donde vive el Docker de n8n) ┌────────────────────────────────────────────────────────────────┐ │ VOLUMEN Docker de n8n (el que ya existe) │ │ └── database.sqlite ← el fichero real │ │ │ │ │ │ montado en n8n montado en el viewer │ │ lectura/escritura SOLO LECTURA (:ro) │ │ │ │ │ │ ┌──────▼───────┐ ┌─────────▼──────────┐ │ │ │ contenedor │ │ contenedor │ │ │ │ n8n (intacto)│ │ n8n-viewer │ │ │ └──────────────┘ └─────────┬──────────┘ │ │ sin contacto entre ambos su PROPIO histórico, │ │ en otro volumen, crece │ │ para siempre │ └────────────────────────────────────────────┬───────────────────┘ │ HTTP :8391 tu proxy / Portainer → usuarios

La garantía de solo-lectura es del kernel, no una promesa del código. Con :ro, aunque el viewer tuviera un bug, el sistema operativo le deniega cualquier escritura sobre el volumen de n8n. Lo único que escribe el viewer es su propio histórico (history.db), en un volumen aparte.

2 · Requisitos previos

RequisitoDetalle
n8n con SQLiteEl modo por defecto de la imagen oficial. Comprueba que exista database.sqlite dentro del volumen de datos de n8n (/home/node/.n8n/database.sqlite). Instancias con Postgres no están soportadas.
Mismo host / kernelEl viewer debe correr en la misma máquina que n8n. Compartir el fichero por NFS o por red no está soportado: SQLite es conocido por corromperse sobre sistemas de ficheros de red.
Construir la imagen una vezNo hay imagen publicada en un registro todavía. En el host donde corre n8n: docker build -t n8n-execution-viewer . (el repo pesa poco; la imagen son tres ficheros Python sobre python:3.12-slim, sin dependencias).
Saber tu volumenTodas las opciones necesitan el nombre del volumen de n8n y dónde se monta dentro del contenedor:
docker inspect <contenedor-de-n8n> --format \
  '{{range .Mounts}}{{.Name}} -> {{.Destination}}{{println}}{{end}}'

# salida típica con la imagen oficial:
#   n8n_data -> /home/node/.n8n
# ⇒ el fichero es /home/node/.n8n/database.sqlite (dentro del volumen)

3 · Opción A — sidecar en tu stack de compose recomendada

Cuándo: tu n8n está definido en un docker-compose.yml (tuyo o del equipo de infra). Es la opción más limpia: el viewer queda declarado junto a n8n, versionado en el mismo fichero, y docker compose up -d levanta ambos tras un reinicio del host.

Cómo: añade este servicio al compose que ya define tu n8n (ajusta n8n_data al nombre real de tu volumen):

services:
  n8n-viewer:
    image: n8n-execution-viewer
    restart: unless-stopped
    environment:
      - N8N_DB_PATH=/data/database.sqlite   # ruta DENTRO del volumen
      # - N8N_VIEWER_RETENTION_DAYS=180     # opcional: conservar N días (0 = siempre)
    volumes:
      - n8n_data:/data:ro                   # el MISMO volumen que usa n8n
      - n8n-viewer_history:/var/lib/n8n-viewer
    ports:
      - "127.0.0.1:8391:8391"               # loopback; delante irá tu proxy

volumes:
  n8n-viewer_history:
  # NO redeclares n8n_data aquí si tu servicio n8n ya lo define en este
  # mismo fichero: reutiliza su nombre tal cual

Ventajas: un solo fichero gobierna todo el stack; el viewer se reinicia, actualiza y respalda con las mismas herramientas que n8n. Contras: tocar el compose de producción puede requerir tu proceso de cambio habitual.

4 · Opción B — contenedor independiente (Portainer o docker run)

Cuándo: gestionas n8n desde la UI de Portainer o con docker run, y prefieres no tocar para nada tu stack de n8n. El viewer es un contenedor nuevo que adjunta el volumen existente de n8n como volumen externo.

Cómo (CLI):

docker volume create n8n-viewer_history

docker run -d --name n8n-viewer --restart unless-stopped \
  -e N8N_DB_PATH=/data/database.sqlite \
  -p 127.0.0.1:8391:8391 \
  -v n8n_data:/data:ro \
  -v n8n-viewer_history:/var/lib/n8n-viewer \
  n8n-execution-viewer

Cómo (Portainer, por UI):

  1. Volumes: localiza el nombre del volumen de datos de tu n8n (el mismo que viste con docker inspect).
  2. Containers → Add container: imagen n8n-execution-viewer, mapeo de puerto 8391 (solo en 127.0.0.1 si tu proxy corre en el host), variable de entorno N8N_DB_PATH=/data/database.sqlite.
  3. En Advanced settings → Volumes, añade dos: el volumen de n8n con el toggle Read-only activado montado en /data, y un volumen nuevo (n8n-viewer_history) montado en /var/lib/n8n-viewer.
  4. Deploy the container. La primera sincronización importa todo el histórico disponible y después avanza sola cada 5 minutos.

Actualizar más adelante: docker rm -f n8n-viewer y vuelve a lanzar el mismo comando — el volumen del histórico no se toca, así que no pierdes ninguna ejecución. Ventajas: cero cambios en tu stack; aíslalo o elimíname cuando quieras. Contras: no queda declarado en ningún compose (documéntalo en tu runbook).

5 · Opción C — servicio nativo, sin segundo contenedor

Cuándo: tu política es un proceso por contenedor, no quieres otra imagen que mantener, o simplemente prefieres un servicio systemd clásico. El instalador detecta el contenedor de n8n que está corriendo, lee la ruta real de su volumen bajo /var/lib/docker/volumes/… y monta el backend como servicio del sistema que lee ese fichero en solo-lectura.

curl -fsSL https://raw.githubusercontent.com/plorentec/n8n-execution-viewer/main/install.sh \
  | sudo bash -s -- \
  --n8n-db /var/lib/docker/volumes/n8n_data/_data/database.sqlite

Con --dry-run ves cada paso sin ejecutar nada; el auto-detección cubre la ruta oficial del volumen y un contenedor en marcha. Copia el frontend a /var/www/n8n-viewer/ y deja preparado Apache si existe. Ventajas: nada nuevo en Docker; gestión con systemctl. Contras: necesitas Python ≥ 3.9 en el host (stdlib, sin paquetes) y el backend corre fuera del aislamiento de Docker.

7 · Servir la interfaz (proxy)

El viewer solo publica su API en 127.0.0.1:8391. La interfaz son ficheros estáticos (frontend/) que sirve cualquier web server. Ejemplos:

Apache (subpath)

Alias /n8n-viewer /var/www/n8n-viewer
ProxyPass /n8n-viewer/api/ http://127.0.0.1:8391/api/
ProxyPassReverse /n8n-viewer/api/ http://127.0.0.1:8391/api/
ProxyPass /n8n-viewer !

nginx (subpath)

location /n8n-viewer/ {
    alias /var/www/n8n-viewer/;
    location /n8n-viewer/api/ { proxy_pass http://127.0.0.1:8391/api/; }
}

Caddy / Traefik

Una ruta estática hacia frontend/ más un router /n8n-viewer/api/* → 127.0.0.1:8391. El frontend usa rutas relativas, así que funciona igual en un subpath o en un subdominio propio (n8n-viewer.tuempresa.com apuntando a la raíz de frontend/).

Protege el acceso. El histórico contiene el texto completo de tus ejecuciones (payloads, credenciales que los flujos manejen…). Restringe por red (LAN/VPN) o pon autenticación delante. En el repo hay un ejemplo de Require ip en deploy/apache-notes.conf.

La marca (título, subtítulo, logo) y la retención se cambian desde la propia UI (engranaje) y se guardan junto al histórico — sobreviven a actualizaciones.

9 · Actualizar sin perder el histórico

  1. git pull del repo (o descarga el tarball del release).
  2. docker build -t n8n-execution-viewer .
  3. Opción A: docker compose up -d n8n-viewer · Opción B: docker rm -f n8n-viewer y el mismo docker run.

El histórico vive en su propio volumen, así que recrear el contenedor nunca borra ejecuciones. La primera vez que la retención borre datos de verdad, el fichero se compacta una única vez (puede tardar unos segundos en históricos grandes; las lecturas siguen funcionando durante ese tiempo).

10 · Copias de seguridad

Lo único con valor único es history.db (y su -wal si existe) en el volumen del histórico. Todo lo demás (contenedor, imagen, frontend) se puede regenerar desde el repo. Un sqlite3 history.db ".backup copia.db" desde cron semanal es suficiente; hacer backup del volumen de n8n no es necesario para este servicio.

11 · Problemas frecuentes

El viewer no abre la base de datos: permission denied

El volumen de n8n pertenece a uid 1000 con ficheros 0600. La imagen corre como root precisamente para poder leerlo (montada :ro, el root del contenedor no puede escribir igualmente). Si corrías el viewer con --user, quítalo o dale acceso de lectura al grupo.

La BD se corrompe / da errores raros de disco

Casi siempre significa que el volumen se comparte por red (NFS/SMB) o que hay dos equipos escribiendo el mismo fichero. SQLite solo es seguro en el mismo kernel: el viewer en el mismo host que n8n, siempre.

Uso Postgres con n8n y el viewer no encuentra ejecuciones

No soportado (todavía): el viewer lee el formato SQLite. Si tu n8n está en Postgres, esta herramienta no es para ti por ahora.

Tras configurar Apache, el API da 404 o el navegador un 502

Recuerda las tres líneas del proxy (incluido ProxyPass /n8n-viewer ! antes de cualquier catch-all): sin la exclusión, tu vhost por defecto se come la ruta. Si usas un dominio con www., cada vhost necesita su propio bloque.

Activé retención y el fichero no encoge

El borrado libera espacio en la siguiente pasada de sincronización que efectivamente borre filas; en históricos creados antes de la v1.0.1 la compactación total ocurre una única vez (VACUUM). Comprueba el progreso con la tarjeta "Disco" de la UI.
